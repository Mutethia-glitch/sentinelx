# Task 24 — Security operations dashboard

Task 24 implements FR-032: a read-only management and SOC overview over real
persisted SentinelX data. It does **not** insert demonstration values, replace
event/alert/incident workflows, or introduce the cross-record search/filter layer
reserved for Task 25.

## Data source and consistency

`GET /api/dashboard` requires the existing `dashboard.read` permission,
available to Administrator, Security Analyst and Viewer/Management. This endpoint
accepts no query parameters and supports GET only.

Each request opens a **PostgreSQL REPEATABLE READ, READ ONLY** transaction and
collects all metrics from one consistent database snapshot. Response timestamp
`asOf` is PostgreSQL `transaction_timestamp()`, not a browser clock or
a hard-coded time. Database/query failures roll the transaction back and produce
a sanitized 503 without exposing credentials, SQL or raw source evidence.

The API returns `{dashboard:{asOf,period,totals,last24Hours,severity,status,
threats,responses,trend}}`. It does not return incident titles, event raw_data,
authentication records, users, IP addresses, or private notifications.

## Metrics and source definitions

All-time totals:
- `eventsTotal`: number of rows in `security_events`;
- `alertsTotal`: number of rows in `alerts`;
- `incidentsTotal`: number of rows in `incidents`;
- `activeIncidents`: incidents whose authoritative status is
  NEW, INVESTIGATING or CONTAINED;
- `newAlerts`: alerts with status NEW;
- `responseActions`: number of recorded `response_actions`;
- `reportedSuccessfulActions` / `reportedFailedActions`: the stored
  Task 22 success flag;
- `successfulContainments`: successful recorded action with type CONTAINMENT;
- `averageIncidentRisk`: PostgreSQL mean of generated Task 20 `risk_score`,
  rounded to one decimal, or null if no incidents exist.

Response success and containment counts are **manual attestations**, not
independently observed endpoint actions. Risk is the documented deterministic
0–100 operational score, not attack probability.

The rolling **last 24 hours** uses the current PostgreSQL snapshot timestamp:
- events received by `security_events.received_at`;
- alerts generated by `alerts.created_at`;
- incidents created by `incidents.created_at`;
- response actions recorded by `response_actions.performed_at`.

Severity distributions cover LOW/MEDIUM/HIGH/CRITICAL separately for alerts and
incidents; missing categories are shown as zero.

Status distributions cover approved alert states NEW/ACKNOWLEDGED and incident
states NEW/INVESTIGATING/CONTAINED/RESOLVED/DISMISSED, all independently zero-filled.

Threat distributions group `alerts.category_code` and
`incidents.category_code` separately and return every persisted category bucket,
ordered by count then stable category code. No approved taxonomy category is
truncated. Null incident classification is represented as UNCLASSIFIED.

Response breakdown groups persisted `response_actions.action` and shows total,
reported successful and reported failed records for each action. The UI renders
the action totals, with overall outcomes displayed in the summary cards.

The seven-day trend includes the **current, possibly partial UTC calendar day**
and six preceding UTC days. Buckets use event receipt time, alert/incident
creation time and response record time. Missing buckets are zero. There is no
arbitrary client-timezone conversion, hidden Task 25 date filter, or time-series
forecast.

## Frontend

`/dashboard` uses the existing authenticated SentinelX application pattern
and restrictive Content Security Policy. A manual Refresh metrics button
retrieves a new authoritative database snapshot; the interface does not claim
live streaming or run an unconfigured background job.

Sections: all-time overview, 24-hour activity, alert/incident severity,
alert/incident status, threat categories, response outcomes and seven-day
trend. Accessible textual counts accompany proportional CSS bars; all data text
is rendered with `textContent`. Empty data shows zero or an explicitly null
mean risk rather than fabricated chart values.

Existing event/alert/access/notification navigation links expose the dashboard.

## Storage and boundaries

Task 24 is read-only and adds **no migration**. Existing migration files 001–014
are unchanged and must remain append-only/checksum protected.

Task 25 will own general date, status, severity, source/IP/user/host/rule/MITRE
cross-record search and filtering. Task 26 owns separately generated reports.

## Verification

The pure tests cover metric mapping, safe aggregate conversion, empty data, live
RBAC, HTTP method/query restrictions, read-only transaction boundary and
sanitized rollback on read failure.

The Windows/PostgreSQL verifier creates synthetic linked evidence, compares
the aggregate results to database counts, records an incident, unsuccessful
manual escalation and successful containment, adjusts incident severity, then
proves that dashboard refresh changes the relevant totals/status/severity
without altering the original event/alert counts or incident risk due to status
alone. Synthetic database changes are cleaned up.

Run:

```powershell
git pull origin main
npm.cmd run quality
node scripts/migrate.js
npm.cmd run verify:dashboard
```

Expected verifier output:

`Live dashboard totals, severity/status distributions, threat and UTC trends, recorded response outcomes, Viewer access, refresh accuracy and read-only rollback verified. Synthetic changes cleaned up.`

For optional PostgreSQL and browser tests **only on a disposable database**:

```powershell
$env:SENTINELX_TEST_DATABASE='1'
npm.cmd run test:dashboard:integration
npm.cmd run test:dashboard:ui
```

No external API key, analytics vendor, new database schema, scheduled job or
commercial SIEM extension is required. Task 25 remains Not Started.
