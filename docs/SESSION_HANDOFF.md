Roles:
- `notifications.read`: Administrator, Security Analyst, Viewer/Management.
- `notifications.send`: Administrator, Security Analyst.
- All inbox/read SQL is explicitly scoped to the authenticated recipient,
  regardless of elevated role.

APIs:
- `GET /api/notifications?status=ALL&page=1` returns only the caller's inbox,
  a distinct unread count and up to 50 records per page. Filters ALL/UNREAD/READ.
- `POST /api/notifications` exact body
  `{recipientId,incidentId,alertId,reason}`; exactly one source ID is non-null,
  reason 1–500 characters, recipient must be active and authorized to read.
- `PATCH /api/notifications/{id}/read` requires `{}`; only recipient succeeds,
  repeat read is a no-op.

Authoritative source severity is snapshotted into LOW/MEDIUM/HIGH/CRITICAL.
Unread items are severity-sorted (CRITICAL/HIGH visually urgent), then timestamp.
Messages are deliberately generic and generated by server with no raw
incident/alert details, passwords, IP addresses or custom sender text.

Only one unread item for a recipient and source is delivered at a time.
Recipient-row locking serializes concurrent sends. A duplicate returns the
existing unread item, 200/deduplicated=true, without a second audit.
New delivery returns 201/delivered=true after the transaction commits.
A read item may be explicitly reissued. Audit failure rolls back both inserts
and mark-read changes; generic errors do not claim success.

`NOTIFICATION_DELIVERED` and `NOTIFICATION_READ` audits are atomic.
A notification never performs Task 22 containment or moves incident status.
Task 22 COMMUNICATION is record-only and distinct from in-app delivery.

The `/notifications` UI includes a private inbox, filtering, unread count,
safe text rendering, mark-as-read and authorized dispatch (including send to self).
`/incidents` and `/alerts` link to the notification page.
